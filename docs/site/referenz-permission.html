    client.permissions.list()client.permissions().list()

    List permissions for a domain object

    Lists raw assignments for one source object. status/person address a person-status or person ID; group_type_role/group_role address their role IDs. group_type collects role-template assignments of that group type; group combines concrete group-role and associated group-type-role assignments, preserving each row’s actual owner domain and ID. Only permission IDs in the currently loaded active definition table are returned. No pagination, explicit ordering, or object-existence check is applied; an unknown owner normally returns an empty list. Intended access is administer persons in churchcore, with a restricted post-administration fallback. The current fallback passes an incomplete key to a boolean permission check and ignores its result; enabled assertions may fail the request. Otherwise direct-domain views restrict authIds to 10130/10131, but combined group/group_type views omit that restriction. This defect must not be treated as an authorization guarantee.

    Search selectable permission assignment targets

    Requires "administer persons" in churchcore. Lists statuses, group-type role templates, concrete group roles, and persons, independently of existing assignments. Archived and inactive targets are included. Without query, lists all targets. Every whitespace-separated search word must match part of the name or its group/group-type context, irrespective of word order. SQL wildcard characters are treated literally. Results use one global pagination, ordered by category (status, group_type_role, group_role, person), name, context name, and domainId. Later categories can therefore start on later pages. Selection does not authorize assigning a specific permission; write endpoints check that separately. Group and role context is returned only for role targets. Authorization filtering and ordering are applied before pagination. Detailed statistics are computed only for the returned page unless required for ordering. Status and role templates include public permissions; concrete roles also inherit their template with applicable revocations. Archived persons have zero effective grants. Counts describe the search/category/group population before authorization filtering. Without these options the original catalog response is retained.

    Save a raw permission assignment

    Adds or updates raw permission assignments for the source owner in the path. Requires administer persons in churchcore, or a group_role assignment for authId 10130/10131 and churchdb +admin posts in that role’s actual group. Locked selections additionally require an authorized person. type defaults to grant; revoke is only supported for group_role. Only role domains allow inheritance and internal authIds; status/person require authId<10000. Obsolete authId=10127 returns 410. dataId is an additive list: other existing selections remain. Omission, null or [] writes a null-data row, not an unrestricted grant; use [-1] for unrestricted selections. An existing -1 row of the same grant/revoke type for the key/inheritance mode causes a nonempty-list update to be ignored, including reason changes. Opposite-type assignments can coexist at different dataIds: a finite grant preserves an existing unrestricted revoke. Otherwise, writing the opposite type for the same selection (including -1) updates that row rather than retaining both types. These rules apply separately to each key/inheritance mode. The general admin path does not validate owner, permission-definition or selection existence. Success returns 204 without a representation; it does not necessarily mean a row changed.
