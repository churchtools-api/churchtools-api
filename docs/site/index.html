    ChurchTools aus Python und Rust ansprechen

    Ein Client für die gesamte ChurchTools-REST-API: typisierte Antworten, Fehler mit verständlicher Meldung, automatisches Blättern durch lange Listen.

    • 875 Endpunkte
    • 1143 Modelle
    • API-Stand ChurchTools 3.139.0 (build 32955) (Änderungen)
    Erster Aufruf Projekte ansehen Zur Referenz

    Einstieg

    Vom Installieren bis zum ersten Aufruf in wenigen Minuten.

    Worum es geht

    churchtools-api ist ein Client für die REST-API von ChurchTools: Personen, Gruppen, Kalender, Events, Dienste, Lieder, Finanzen und alles Weitere, was die API anbietet.

    Es gibt ihn für zwei Sprachen. Beide entstehen aus derselben API-Beschreibung und funktionieren gleich:

    • Python: Rückgaben sind Pydantic-Modelle mit Autovervollständigung in der IDE.
    • Rust: Rückgaben sind serde-Structs, Fehler sind ein Result.

    Wähle oben rechts deine Sprache. Alle Beispiele auf dieser Seite wechseln mit.

    Was du brauchst

    • Die Adresse deiner ChurchTools-Instanz, z. B. https://meinegemeinde.church.tools.
    • Ein Login-Token für alles, was nicht öffentlich ist. Das Token gehört zu einer Person in ChurchTools, und der Client sieht genau das, was diese Person sehen darf. Für Skripte lohnt sich ein eigener Benutzer mit passend eingeschränkten Rechten.

    Öffentliche Daten wie öffentliche Kalender funktionieren auch ohne Token. Damit kannst du sofort loslegen.

    Installation

    Das Rust-Crate heißt churchtools-api, das Python-Paket churchtools-api-rs; importiert wird es als churchtools_api. (Der Name churchtools-api ist auf PyPI wegen eines älteren, nicht verwandten Projekts gesperrt.)

    • Python: pip install churchtools-api-rs (ab Python 3.10). Für Linux (x86-64, ARM64, auch musl), macOS (Intel und Apple Silicon) und Windows (x86-64) gibt es fertige Wheels; ein Wheel deckt alle Python-Versionen ab 3.10 ab. Auf anderen Plattformen baut pip das Paket aus dem Quellcode mit maturin; dafür braucht es eine Rust-Toolchain ab 1.88 und einen C-Compiler (für die TLS-Bibliothek; unter Linux gcc oder clang, unter macOS die Xcode-Kommandozeilenwerkzeuge, unter Windows die Visual-Studio-Build-Tools).
    • Rust: cargo add churchtools-api (ab Rust 1.88). Auch hier wird ein C-Compiler gebraucht.

    Den neuesten Entwicklungsstand bekommst du direkt aus dem Git-Repository.

    pip install churchtools-api-rs

# Entwicklungsstand aus dem Git-Repository (baut aus dem Quellcode)
pip install "churchtools-api-rs @ git+https://github.com/churchtools-api/churchtools-api#subdirectory=python"
    # Cargo.toml
[dependencies]
churchtools-api = "0.3"
# oder der Entwicklungsstand aus dem Git-Repository
churchtools-api = { git = "https://github.com/churchtools-api/churchtools-api" }

    Dein erster Aufruf

    Dieses Programm fragt ab, welche ChurchTools-Version eine Instanz verwendet. Es braucht kein Token und läuft gegen die öffentliche Demo-Instanz.

    Danach bist du startklar. Die folgenden Beispiele zeigen nur noch den Teil, der sich ändert, und setzen einen fertigen client voraus.

    import churchtools_api as ct

client = ct.Client("https://demo.church.tools")
info = client.info.get()
print(info.site_name, info.version)
    use churchtools_api::Client;

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let client = Client::new("https://demo.church.tools", None)?;
    let info = client.info().get()?;
    println!("{:?} {:?}", info.site_name, info.version);
    Ok(())
}

    Grundlagen

    Die Konzepte, die für jeden Aufruf gelten. Wer sie kennt, findet sich in der ganzen Referenz zurecht.

    Client und Anmeldung

    Ein Client gehört zu einer Instanz und einem Token. Das Token wird als Authorization: Login <token> mitgeschickt. Du musst dich um nichts weiter kümmern.

    Lege das Token nicht in den Quelltext. Am einfachsten liest du es aus den Umgebungsvariablen CT_URL und CT_TOKEN.

    import churchtools_api as ct

client = ct.Client("https://meinegemeinde.church.tools", token="DEIN_TOKEN")

# besser: CT_URL und CT_TOKEN aus der Umgebung lesen
client = ct.Client.from_env()

me = client.whoami.get()
print(f"Angemeldet als {me.first_name} {me.last_name}")
    use churchtools_api::Client;

let client = Client::new("https://meinegemeinde.church.tools", Some("DEIN_TOKEN".into()))?;

// besser: CT_URL und CT_TOKEN aus der Umgebung lesen
let client = Client::from_env()?;

let me = client.whoami().get()?;
println!("Angemeldet als {:?} {:?}", me.first_name, me.last_name);

    Anfragen drosseln

    Für Skripte, die viele Anfragen schicken, kannst du einen Mindestabstand zwischen zwei Anfragen festlegen. So belastest du die Instanz nicht unnötig. Der Abstand gilt auch für Kopien des Clients.

    Antwortet der Server mit 429 Too Many Requests, wartet der Client die verlangte Zeit (Retry-After, höchstens 60 Sekunden) und versucht es bis zu dreimal erneut. Das passiert immer, auch ohne Mindestabstand. Bei 502, 503 und 504 wiederholt er lesende und andere idempotente Anfragen (GET, PUT, DELETE) genauso; ein POST wird nicht wiederholt, weil er sonst doppelt ausgeführt werden könnte. Kommt keine Verbindung zustande, versucht er es nach einer Sekunde einmal erneut.

    Für Tests gegen eine Demo-Instanz gibt es außerdem login_with_password. Es meldet sich mit Benutzername und Passwort an und holt das Login-Token der Person. In eigenen Skripten ist ein gespeichertes Token besser.

    # höchstens vier Anfragen pro Sekunde
client = ct.Client.from_env(min_interval=0.25)

for person in client.persons.list():
    print(person.id, person.first_name)

# nur für Tests: mit Benutzername und Passwort anmelden
test = ct.Client("https://xyz.church.tools").login_with_password("benutzer", "passwort")
    use std::time::Duration;

// höchstens vier Anfragen pro Sekunde
let client = Client::from_env()?.with_min_interval(Duration::from_millis(250));

for person in client.persons().list()? {
    println!("{} {:?}", person.id, person.first_name);
}

// nur für Tests: mit Benutzername und Passwort anmelden
let test = Client::new("https://xyz.church.tools", None)?.login_with_password("benutzer", "passwort")?;

    Wie Aufrufe aufgebaut sind

    Jeder Aufruf folgt dem Pfad der API. Aus jedem festen Teil des Pfads wird eine Ressource. Platzhalter wie {groupId} werden zu Argumenten:

    APIPythonRust
    GET /groupsclient.groups.list()client.groups().list()
    GET /groups/{groupId}client.groups.get(42)client.groups().get(42)
    GET /groups/{groupId}/membersclient.groups.members.list(42)client.groups().members().list(42)

    Der Methodenname richtet sich nach der HTTP-Methode:

    HTTPMethodebedeutet
    GETlist / getmehrere lesen / eins lesen
    POSTcreateneu anlegen
    PUTupdateersetzen oder setzen
    PATCHpatcheinzelne Felder ändern
    DELETEdeletelöschen

    Aktionen behalten ihren Namen, z. B. client.persons.invite(7) für POST /persons/{personId}/invite. POST-Aufrufe, die nichts anlegen, sondern nur lesen oder berechnen, heißen nach dem, was sie tun: client.actions.filter(), client.repeat_calculation.calculate().

    Zusammengeschriebene Pfadteile werden in Wörter getrennt: /agendatemplates wird zu agenda_templates, genauso wie /external-logins zu external_logins.

    Einige Bereiche gibt es im Singular und im Plural. Der Plural enthält die Objekte selbst, der Singular die Stammdaten des Bereichs: client.groups sind die Gruppen, client.group ihre Gruppentypen, Rollen und Kategorien. Genauso persons/person, events/event und posts/post.

    group = client.groups.get(42)
print(group.name)

for member in client.groups.members.list(42):
    print(member.person.title)
    let group = client.groups().get(42)?;
println!("{}", group.name);

for member in client.groups().members().list(42)? {
    println!("{}", member.person.title);
}

    Parameter übergeben

    Es gibt drei Arten von Parametern:

    • Pfad: Platzhalter im Pfad. Sie stehen vorne und haben keinen Namen.
    • Query: Filter und Optionen wie from, to, limit. In Python sind das Schlüsselwort-Argumente. In Rust gibt es dafür eine …Query-Struktur. Sind alle Filter optional, hat die Methode zwei Varianten: list() ohne Filter und list_with(&query) mit Filtern. ..Default::default() füllt alles, was du nicht setzt.
    • Body: Daten zum Anlegen oder Ändern. In Python sind es ebenfalls Schlüsselwort-Argumente, in Rust ein Modell als Struct-Literal. Auch hier füllt ..Default::default() alle Felder, die du nicht setzt.

    Die Namen sind in Python im üblichen snake_case geschrieben (first_name statt firstName). Wo ein Name ein Python-Schlüsselwort ist, kommt ein Unterstrich dazu: from_.

    Hat ein Wert eine feste Auswahl (z. B. group_member_status: active, requested, waiting, …), steht sie in der Doku unter „Allowed values“. In Python ist das Argument als Literal[...] typisiert: Die IDE schlägt die Werte vor, und mypy meldet Tippfehler. In Antworten ist zusätzlich jeder str erlaubt, damit ein neuer Wert einer neueren ChurchTools-Version nicht zu einem Fehler führt. In Rust sind solche Werte String.

    import datetime as dt

persons = client.persons.list(last_name="Müller", is_archived=False)

events = client.events.list(from_=dt.date(2026, 11, 1), to=dt.date(2026, 11, 30))

client.persons.patch(7, city="Esslingen", zip="73728")
    let query = GetPersonsQuery {
    last_name: Some("Müller".into()),
    is_archived: Some(false),
    ..Default::default()
};
let persons = client.persons().list_with(&query)?;

let query = GetEventsQuery {
    from: Some("2026-11-01".parse()?),
    to: Some("2026-11-30".parse()?),
    ..Default::default()
};
let events = client.events().list_with(&query)?;

let body = models::PatchPersonsIdBody {
    city: Some(Some("Esslingen".into())),
    zip: Some(Some("73728".into())),
    ..Default::default()
};
client.persons().patch(7, &body)?;

    Rückgabewerte und Modelle

    Antworten kommen als typisierte Objekte zurück. Die Felder heißen wie in der API, nur in snake_case.

    Jede ChurchTools-Instanz kann eigene Datenbankfelder haben, die in keiner Beschreibung stehen. Diese Felder gehen nicht verloren: In Python liegen sie in model_extra, in Rust im Feld extra.

    Willst du ein Objekt weitergeben oder speichern, wandelst du es in ein Dict oder JSON um.

    person = client.persons.get(7)
print(person.first_name, person.birthday)

# eigene Felder der Instanz
print(person.model_extra)

# als dict / JSON (mit den Feldnamen der API)
data = person.model_dump(exclude_none=True)
text = person.model_dump_json()
    let person = client.persons().get(7)?;
println!("{:?} {:?}", person.first_name, person.birthday);

// eigene Felder der Instanz
println!("{:?}", person.extra);

// als JSON (mit den Feldnamen der API)
let text = serde_json::to_string(&person)?;

    Listen und Seiten

    Große Listen liefert ChurchTools seitenweise. Der Client blättert für dich:

    • In Python bekommst du einen Paginator. Er lädt Seiten erst, wenn du sie brauchst: first() holt nur das erste Element, to_list() alles. Brichst du die Schleife ab, werden keine weiteren Seiten geladen.
    • In Rust liefert list() gleich einen Vec mit allen Einträgen. list_iter(&query) lädt dagegen wie in Python erst beim Iterieren nach; jedes Element ist ein Result.

    Mit limit bestimmst du, wie viele Einträge pro Seite geladen werden (höchstens 100).

    Ab der zweiten Seite fordert der Client die jeweils nächste Seite in einem Hintergrund-Thread an, während du die aktuelle verarbeitest. Die Wartezeit auf den Server überlappt so mit dem Dekodieren und deiner Verarbeitung. Brichst du eine Schleife mitten in einer späteren Seite ab, kann dadurch eine Anfrage mehr unterwegs sein; ihre Antwort wird verworfen. Mit .prefetch(False) (Python) bzw. .prefetch(false) (Rust) wird jede Seite erst angefordert, wenn sie gebraucht wird.

    Die Seiten werden nacheinander abgerufen. Ändert sich die Liste währenddessen, etwa weil jemand eine Person anlegt oder löscht, kann ein Eintrag doppelt vorkommen oder fehlen. Für Abgleiche lohnt es sich deshalb, nach id zu deduplizieren. Eine leere Seite beendet das Blättern, auch wenn der Server mehr Seiten ankündigt.

    Der Client ist synchron. In Rust darfst du ihn nicht direkt in async-Code (Tokio) aufrufen, sondern nur über tokio::task::spawn_blocking.

    for person in client.persons.list(limit=100):
    print(person.last_name)
    if person.last_name == "Zimmermann":
        break               # weitere Seiten werden nicht mehr geladen

first = client.groups.list().first()
all_groups = client.groups.list().to_list()
    let query = GetPersonsQuery { limit: Some(100), ..Default::default() };
for person in client.persons().list_iter(&query) {
    let person = person?;
    println!("{:?}", person.last_name);
    if person.last_name.as_deref() == Some("Zimmermann") {
        break;              // weitere Seiten werden nicht mehr geladen
    }
}

let all_groups = client.groups().list()?;

    Datum und Uhrzeit

    Datumswerte (Geburtstage, ganztägige Termine) sind reine Kalenderdaten. Zeitpunkte kommen immer in UTC und mit Zeitzone. Für die Anzeige rechnest du sie in die lokale Zeit um.

    Termine können beides sein: Ganztägige Termine haben nur ein Datum, alle anderen einen Zeitpunkt.

    import datetime as dt
from zoneinfo import ZoneInfo

berlin = ZoneInfo("Europe/Berlin")
event = client.events.get(42)
print(event.start_date.astimezone(berlin))   # 2026-11-01 10:00:00+01:00

# date | datetime: erst prüfen, was es ist
appointment = client.calendars.appointments.get_occurrence(42, dt.date(2026, 11, 1))
start = appointment.appointment.calculated.start_date
if isinstance(start, dt.datetime):
    print("um", start.astimezone(berlin).strftime("%H:%M"))
else:
    print("ganztägig am", start)
    use churchtools_api::chrono::Local;

let event = client.events().get(42)?;
println!("{}", event.start_date.with_timezone(&Local));

// DateOrDateTime: erst prüfen, was es ist
let appointment = client.calendars().appointments()
    .get_occurrence(42, "2026-11-01")?;
match appointment.appointment.calculated.start_date {
    DateOrDateTime::DateTime(t) => println!("um {}", t.with_timezone(&Local).format("%H:%M")),
    DateOrDateTime::Date(d) => println!("ganztägig am {d}"),
}

    Fehler behandeln

    Antwortet ChurchTools mit einem Fehler, bekommst du die Meldung des Servers, auf Wunsch auch in der übersetzten Fassung (translated_message). In Python gibt es für die häufigsten Statuscodes eigene Ausnahmen, siehe die Fehlerübersicht. In Rust gibt es dafür is_not_found(), is_unauthorized(), is_forbidden(), is_timeout() und status(). Weil neue Fehlerarten dazukommen können, braucht ein match über Error immer einen Zweig _ bzw. Err(e).

    try:
    person = client.persons.get(999999)
except ct.NotFound:
    print("Diese Person gibt es nicht.")
except ct.Unauthorized:
    print("Token fehlt oder ist abgelaufen.")
except ct.ApiError as e:
    print(e.status, e.translated_message)
    use churchtools_api::Error;

match client.persons().get(999999) {
    Ok(person) => println!("{:?}", person.first_name),
    Err(e) if e.is_not_found() => println!("Diese Person gibt es nicht."),
    Err(e) if e.is_unauthorized() => println!("Token fehlt oder ist abgelaufen."),
    Err(Error::Api(e)) => println!("{} {:?}", e.status, e.translated_message),
    Err(e) => return Err(e.into()),
}

    Felder weglassen oder leeren

    Beim Ändern macht es einen Unterschied, ob ein Feld fehlt oder leer ist:

    • Weggelassen: Das Feld bleibt, wie es ist. In Python ist das der Standard (UNSET), in Rust None, das ..Default::default() setzt.
    • **None / null**: Das Feld wird geleert. In Rust haben Felder, die man leeren kann, den Typ Option<Option<T>>; Some(None) schickt null.

    Felder, die der Client nicht kennt (z. B. eigene DB-Felder), übergibst du in Python mit extra_body, in Rust über das Feld extra.

    # nur die Stadt ändern, alles andere bleibt
client.persons.patch(7, city="Esslingen")

# Geburtstag löschen
client.persons.patch(7, birthday=None)

# eigenes Datenbankfeld setzen
client.persons.patch(7, extra_body={"konfession": "evangelisch"})
    // nur die Stadt ändern, alles andere bleibt
let body = models::PatchPersonsIdBody { city: Some(Some("Esslingen".into())), ..Default::default() };
client.persons().patch(7, &body)?;

// Geburtstag löschen
let body = models::PatchPersonsIdBody { birthday: Some(None), ..Default::default() };
client.persons().patch(7, &body)?;

// eigenes Datenbankfeld setzen
let mut body = models::PatchPersonsIdBody::default();
body.extra.insert("konfession".into(), "evangelisch".into());
client.persons().patch(7, &body)?;

    Dateien hochladen und herunterladen

    Endpunkte mit Datei-Upload nehmen eine Liste von Upload-Objekten. Upload.from_path liest eine Datei und leitet den Dateityp aus der Endung ab; Upload(name, inhalt, typ) nimmt Bytes aus dem Speicher.

    Downloads (PDF, CSV, Excel, Bilder) kommen als Bytes zurück, die du direkt speichern kannst.

    import churchtools_api as ct

# an eine Person anhängen
client.files.create("person", "7", files=[ct.Upload.from_path("brief.pdf")])

# aus dem Speicher
client.files.create("person", "7", files=[ct.Upload("notiz.txt", b"Hallo", "text/plain")])

# herunterladen
data = client.groups.members.get_export(42)
with open("mitglieder.xlsx", "wb") as f:
    f.write(data)
    let file = Upload::from_path("brief.pdf")?;
client.files().create("person", 7, &[file])?;

let note = Upload::new("notiz.txt", b"Hallo".to_vec(), "text/plain");
client.files().create("person", 7, &[note])?;

let data = client.groups().members().get_export(42)?;
std::fs::write("mitglieder.xlsx", &data)?;

    Zeitlimits und große Antworten

    Ohne weitere Angaben gelten diese Grenzen:

    EinstellungStandardbedeutet
    timeout30 sdie ganze Anfrage inklusive Antwort
    connect_timeout10 snur der Verbindungsaufbau, höchstens timeout
    max_response_size256 MiBgrößere Antworten brechen mit ResponseTooLarge ab

    Für große Exporte und Uploads lohnt ein längeres timeout. Ein kurzes connect_timeout sorgt dafür, dass eine nicht erreichbare Instanz schnell auffällt. Zu langsame Anfragen enden mit Timeout, fehlende Verbindungen mit ConnectError; in Rust prüfst du is_timeout() und is_connect().

    client = ct.Client(
    "https://meinegemeinde.church.tools",
    token="DEIN_TOKEN",
    timeout=300,            # große Exporte
    connect_timeout=5,
    max_response_size=1024**3,
)
    use std::time::Duration;

let client = Client::builder("https://meinegemeinde.church.tools")
    .token(Some("DEIN_TOKEN".into()))
    .timeout(Duration::from_secs(300))
    .connect_timeout(Duration::from_secs(5))
    .max_response_size(1 << 30)
    .build()?;

    Endpunkte ohne generierte Methode

    Manche Endpunkte stehen nicht in der API-Beschreibung, etwa ganz neue oder interne. Für sie gibt es client.request: Methode, Pfad unterhalb von /api, Query und JSON-Body. Zurück kommen die rohen Bytes, Fehler sind dieselben Ausnahmen wie sonst. Login, Drosselung und Wiederholungen gelten auch hier.

    Die Antwort wandelst du mit json.loads oder direkt in ein Modell um.

    import json

body = client.request("GET", "/persons/7", query={"include": ["tags"]})
person = ct.models.Person.model_validate(json.loads(body)["data"])

client.request("POST", "/persons", json={"departmentIds": [1], "firstName": "Ben"})
    let query = vec![("include[]".to_string(), "tags".to_string())];
let person: models::Person = client.request_data(Method::Get, "/persons/7", &query, None)?;

let body = serde_json::json!({ "departmentIds": [1], "firstName": "Ben" });
client.request(Method::Post, "/persons", &[], Some(&body))?;

    ChurchTools-Versionen

    Der Client ist aus der API-Beschreibung einer bestimmten ChurchTools-Version erzeugt. Welche das ist, steht in API_VERSION (z. B. 3.138.1). Gegen andere Versionen funktioniert er, soweit die API gleich ist:

    • Neue Felder einer neueren Version gehen nicht verloren: Sie landen in model_extra bzw. extra.
    • Neue Werte in Feldern mit fester Auswahl führen nicht zu Fehlern, Antworten erlauben jeden str.
    • Fehlende Endpunkte einer älteren Version antworten mit 404.
    • Geänderte Pflichtfelder können ein DecodeError auslösen. Dann hilft eine neuere Version des Clients.

    Die eigene Version (__version__, in Rust die Crate-Version) folgt SemVer. Was sich ändert, steht im CHANGELOG.md. Neue ChurchTools-Versionen bringen meist eine neue Minor-Version.

    import churchtools_api as ct

info = client.info.get()
if info.version != ct.API_VERSION:
    print(f"Instanz {info.version}, Client erzeugt für {ct.API_VERSION} (Version {ct.__version__})")
    let info = client.info().get()?;
if info.version.as_deref() != Some(churchtools_api::API_VERSION) {
    println!("Instanz {:?}, Client erzeugt für {}", info.version, churchtools_api::API_VERSION);
}

    Projekte

    Kleine, vollständige Aufgaben aus dem Gemeindealltag. Jedes Projekt verbindet mehrere Aufrufe.

    Monatsplan aus öffentlichen Kalendern

    Ziel: alle Termine eines Monats aus allen öffentlichen Kalendern, sortiert und in Ortszeit.

    1. Kalender laden und ihre IDs sammeln.
    2. Die Termine aller Kalender in einem Aufruf holen.
    3. Ganztägige Termine und Termine mit Uhrzeit unterschiedlich ausgeben.

    Das funktioniert ohne Token, solange die Kalender öffentlich sind.

    import datetime as dt
from zoneinfo import ZoneInfo

berlin = ZoneInfo("Europe/Berlin")

    Heizung nach Raumbuchungen steuern

    Ziel: Räume nur dann heizen, wenn sie gebucht sind. Ein Skript läuft regelmäßig, etwa alle 15 Minuten per Cron oder systemd-Timer, schaut in die Raumbuchungen und stellt für jeden Raum die passende Temperatur ein: rechtzeitig vor der Buchung warm, sonst abgesenkt.

    1. Die Räume laden und auf die mit Heizkreis beschränken. Welcher Raum zu welchem Heizkreis gehört, legst du einmal fest; hier über den Namen der Ressource.
    2. Die bestätigten Buchungen dieser Räume für die nächsten sieben Tage holen (status_ids=[2]; 1 sind Anfragen, 3 abgelehnte Buchungen). Wiederkehrende Buchungen kommen dabei schon als einzelne Termine.
    3. Für jede Buchung eine Heizzeit berechnen: Beginn minus Vorlauf bis Ende. Ganztägige Buchungen haben ein Datum statt einer Uhrzeit und heizen den ganzen Tag.
    4. Ist der Raum jetzt in einer Heizzeit, Komfort-Temperatur setzen, sonst Absenk-Temperatur.

    Die Heizung selbst ist hier nur ein Platzhalter, der ausgibt, was er tun würde. In der Praxis stünde dort der Aufruf an die Heizungssteuerung, etwa die API von Home Assistant, ein KNX-Gateway oder die Cloud des Thermostat-Herstellers. Weil das Skript bei jedem Lauf den Sollwert neu aus den Buchungen ableitet, braucht es keinen eigenen Zustand: Wird eine Buchung verschoben oder abgesagt, stimmt die Heizung beim nächsten Lauf.

    Der Token-Benutzer braucht Leserechte für die Räume in der Ressourcenverwaltung.

    import datetime as dt
from zoneinfo import ZoneInfo

# Einstellungen: Vorlauf, Temperaturen und welcher Raum zu welchem Heizkreis gehört
berlin = ZoneInfo("Europe/Berlin")
VORLAUF = dt.timedelta(hours=2)  # so lange braucht ein Raum zum Aufheizen
KOMFORT, ABSENKUNG = 21.0, 16.0
HEIZKREISE = {"Saal": "heizkreis-saal", "Kapelle": "heizkreis-kapelle"}


class Heizung:
    """Platzhalter für die echte Heizungssteuerung."""

    def setze(self, heizkreis: str, grad: float) -> None:
        print(f"  → {heizkreis}: {grad} °C")


def als_zeit(wert: dt.date | dt.datetime, ende: bool = False) -> dt.datetime:
    """Zeitpunkt in Ortszeit; ganztägige Buchungen reichen bis zum Ende des Tags."""
    if isinstance(wert, dt.datetime):
        return wert.astimezone(berlin)
    tag = wert + dt.timedelta(days=1) if ende else wert
    return dt.datetime.combine(tag, dt.time(), berlin)


# 1. Räume mit Heizkreis: Ressourcen-ID → Name
raeume = {r.id: r.name for r in client.resources.list() if r.name in HEIZKREISE}

# 2. Bestätigte Buchungen dieser Räume für die nächsten sieben Tage
heute = dt.date.today()
buchungen = client.bookings.list(
    resource_ids=list(raeume),
    status_ids=[2],  # 1 = angefragt, 2 = bestätigt, 3 = abgelehnt
    from_=heute,
    to=heute + dt.timedelta(days=7),
)

# 3. Heizzeiten pro Raum: Beginn minus Vorlauf bis Ende der Buchung
heizzeiten: dict[str, list[tuple[dt.datetime, dt.datetime, str]]] = {
    name: [] for name in raeume.values()
}
for eintrag in buchungen:
    buchung, termin = eintrag.booking.base, eintrag.booking.calculated
    if buchung.resource_id not in raeume:
        continue
    start = als_zeit(termin.start_date) - VORLAUF
    ende = als_zeit(termin.end_date, ende=True)
    heizzeiten[raeume[buchung.resource_id]].append((start, ende, buchung.title))

# 4. Plan ausgeben und für jeden Raum die Temperatur setzen, die jetzt gilt
jetzt = dt.datetime.now(berlin)
heizung = Heizung()
for raum, zeiten in heizzeiten.items():
    print(raum)
    for start, ende, titel in sorted(zeiten):
        print(f"  heizen {start:%d.%m. %H:%M} – {ende:%d.%m. %H:%M}  {titel}")
    belegt = any(start <= jetzt < ende for start, ende, _ in zeiten)
    heizung.setze(HEIZKREISE[raum], KOMFORT if belegt else ABSENKUNG)
    use std::collections::HashMap;
use churchtools_api::chrono::{DateTime, Days, Local, NaiveTime, TimeDelta, TimeZone};

// Einstellungen: Vorlauf, Temperaturen und welcher Raum zu welchem Heizkreis gehört
const KOMFORT: f64 = 21.0;
const ABSENKUNG: f64 = 16.0;
let vorlauf = TimeDelta::hours(2); // so lange braucht ein Raum zum Aufheizen
let heizkreise = HashMap::from([("Saal", "heizkreis-saal"), ("Kapelle", "heizkreis-kapelle")]);

/// Platzhalter für die echte Heizungssteuerung.
fn setze_heizung(heizkreis: &str, grad: f64) {
    println!("  → {heizkreis}: {grad} °C");
}

/// Zeitpunkt in Ortszeit; ganztägige Buchungen reichen bis zum Ende des Tags.
fn als_zeit(wert: &DateOrDateTime, ende: bool) -> DateTime<Local> {
    match wert {
        DateOrDateTime::DateTime(t) => t.with_timezone(&Local),
        DateOrDateTime::Date(d) => {
            let tag = if ende { d.checked_add_days(Days::new(1)).unwrap_or(*d) } else { *d };
            let mitternacht = tag.and_time(NaiveTime::MIN);
            Local.from_local_datetime(&mitternacht).earliest().unwrap_or_else(Local::now)
        }
    }
}

// 1. Räume mit Heizkreis: Ressourcen-ID → Name
let raeume: HashMap<i64, String> = client
    .resources()
    .list()?
    .into_iter()
    .filter(|r| heizkreise.contains_key(r.name.as_str()))
    .map(|r| (r.id, r.name))
    .collect();

// 2. Bestätigte Buchungen dieser Räume für die nächsten sieben Tage
let heute = Local::now().date_naive();
let query = GetBookingsQuery {
    resource_ids: Some(raeume.keys().copied().collect()),
    status_ids: Some(vec![2]), // 1 = angefragt, 2 = bestätigt, 3 = abgelehnt
    from: Some(heute),
    to: heute.checked_add_days(Days::new(7)),
    ..Default::default()
};

// 3. Heizzeiten pro Raum: Beginn minus Vorlauf bis Ende der Buchung
let mut heizzeiten: HashMap<&str, Vec<(DateTime<Local>, DateTime<Local>, String)>> =
    HashMap::new();
for eintrag in client.bookings().list(&query)? {
    let (buchung, termin) = (eintrag.booking.base, eintrag.booking.calculated);
    let Some(raum) = raeume.get(&buchung.resource_id) else { continue };
    let start = als_zeit(&termin.start_date, false) - vorlauf;
    let ende = als_zeit(&termin.end_date, true);
    heizzeiten.entry(raum.as_str()).or_default().push((start, ende, buchung.title));
}

// 4. Plan ausgeben und für jeden Raum die Temperatur setzen, die jetzt gilt
let jetzt = Local::now();
for raum in raeume.values() {
    println!("{raum}");
    let mut zeiten = heizzeiten.remove(raum.as_str()).unwrap_or_default();
    zeiten.sort();
    for (start, ende, titel) in &zeiten {
        let (von, bis) = (start.format("%d.%m. %H:%M"), ende.format("%d.%m. %H:%M"));
        println!("  heizen {von} – {bis}  {titel}");
    }
    let belegt = zeiten.iter().any(|(start, ende, _)| *start <= jetzt && jetzt < *ende);
    setze_heizung(heizkreise[raum.as_str()], if belegt { KOMFORT } else { ABSENKUNG });
}

    Testen

    Skripte ausprobieren, ohne echte Gemeindedaten anzufassen.

    Mit einer Demo-Instanz testen

    Für eigene Versuche bietet ChurchTools eine kostenlose Test-Instanz an. Sie ist mit erfundenen Beispieldaten einer Gemeinde gefüllt, du bist darin Administrator, und nach drei Tagen wird sie gelöscht. Dort kannst du auch schreibende Aufrufe ausprobieren, ohne etwas kaputtzumachen.

    1. Auf der Seite oben eine Test-Instanz anfordern. Adresse, Benutzername und Passwort kommen per E-Mail.
    2. Die Zugangsdaten als Umgebungsvariablen setzen, nicht in den Quelltext schreiben.
    3. Im Skript mit login_with_password anmelden und min_interval setzen, damit die Instanz nicht mit Anfragen überflutet wird.

    login_with_password holt das dauerhafte Login-Token des Benutzers. Für eine Demo-Instanz ist das in Ordnung; in einer echten Instanz legst du besser einen eigenen Benutzer mit passenden Rechten an und speicherst dessen Token.

    Teste nie gegen eine Produktivinstanz, wenn dein Skript Daten anlegt oder löscht.

    import os
import churchtools_api as ct

demo = ct.Client(os.environ["CT_URL"], min_interval=0.25)
client = demo.login_with_password(os.environ["CT_USER"], os.environ["CT_PASSWORD"])

me = client.whoami.get()
print(f"Angemeldet als {me.first_name} {me.last_name}")
print(sum(1 for _ in client.persons.list()), "Personen in der Demo")

    Die Tests dieses Projekts gegen eine Demo-Instanz

    Das Projekt prüft jeden Endpunkt gegen eine echte Instanz. Diese Live-Tests legen Daten an und löschen sie wieder, deshalb laufen sie nur gegen eine Demo-Instanz. Sie dauern etwa vier Minuten.

    • pytest tests/live ruft jeden GET-Endpunkt auf und spielt Schreib-Szenarien durch (anlegen, ändern, löschen). Ohne CT_URL und Zugangsdaten werden sie übersprungen.
    • Die Antworten landen in fixtures/recorded/. Zugangsdaten und der Name der Instanz werden dabei ersetzt (gemeinde.example). Aus den Aufzeichnungen entstehen die Offline-Tests, die ohne Netz laufen.
    • python tests/live/summary.py fasst das Ergebnis zusammen, fixtures/live-results.json hält es pro Endpunkt fest. Die Testabdeckung dieser Seite stammt daraus.

    Vor dem Einchecken neuer Aufzeichnungen lohnt ein Blick hinein: Die Demo enthält neben den erfundenen Personen auch öffentliche Inhalte von ChurchTools, etwa Blog- und News-Beiträge.

python tests/live/summary.py

    Testabdeckung

    Alle Endpunkte werden gegen eine echte ChurchTools-Testinstanz geprüft. Ein rotes Sternchen * an einem Endpunkt heißt: noch nicht oder nicht ausreichend getestet. Fährst du mit der Maus darüber, steht dort der Grund.

    • kein Testszenario: Der Aufruf wurde bewusst nicht ausgeführt, etwa weil er E-Mails verschickt, Logins oder Rechte ändert oder ein externes System braucht.
    • keine Testdaten: Die Testinstanz hatte nichts, worauf sich der Aufruf anwenden ließ, und es ließ sich auch nicht über die API anlegen.
    • getestet, Fehler der API: Der Aufruf scheitert auch auf der Testinstanz, mit bekannter Ursache, meist einem Fehler in ChurchTools.

    Die Beispiele auf dieser Seite sind Teil der Tests: Alle werden kompiliert bzw. typgeprüft, und die Beispiele zu getesteten Endpunkten laufen gegen die aufgezeichneten Antworten der Testinstanz.

    Ohne Sternchen heißt: Der Aufruf lief erfolgreich, und die Antwort passte zu den Typen in Python und Rust. Das garantiert nicht jede Kombination von Parametern. Details stehen im Testbericht (docs/testbericht.md).
