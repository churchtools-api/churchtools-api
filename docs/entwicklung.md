# Entwicklung

Wie das Projekt aufgebaut ist, wie man es baut und testet, und wie der Generator mit der API-Beschreibung umgeht.
Für Nutzer des Clients ist das [README](../README.md) und die [Doku-Seite](site/index.html) gedacht.

## Aufbau

```
core/      churchtools-api: Rust-Crate (reqwest blocking + serde)
python/    churchtools-api-rs:  PyO3-Erweiterung `_core` + Python-Paket `churchtools_api`
codegen/   generate.py:     openapi.json -> Rust- und Python-Code, OPERATIONS.md, Doku
           guide.py:        handgeschriebene Doku-Texte und Projekt-Beispiele
           examples.py:     erzeugt die Referenz-Beispiele
docs/      site/index.html: generierte Doku-Seite; testbericht.md: Ergebnis der Live-Tests
fixtures/  aufgezeichnete Antworten der Demo-Instanz (bereinigt), Grundlage der Offline-Tests
benchmarks/ eigener Cargo-Workspace, siehe benchmarks/README.md
```

Die Aufgaben sind so aufgeteilt:

| | Rust (`core`) | Python (`churchtools_api`) |
|---|---|---|
| HTTP, Login-Token, Timeouts | ✔ (auch für Python) | |
| Rate-Limit (`min_interval`), Retry bei `429`/`5xx` | ✔ (auch für Python) | |
| Paginierung (`meta.pagination`) | ✔ (auch für Python) | Iterator darüber |
| Fehler aus dem Response-Body | `ApiError` | `NotFound`, `Unauthorized`, ... |
| Typen | serde-Structs (generiert) | Pydantic-Modelle (generiert) |
| Endpunkte | `client.events().list(&query)` (generiert) | `client.events.list(...)` (generiert) |

Die Python-Seite verwendet die Rust-Structs nicht. Rust liefert die rohen JSON-Bytes, Pydantic validiert sie direkt
(`validate_json`, ebenfalls in Rust implementiert). Beide Typsysteme entstehen aus derselben Spec.

Generierte Dateien (Kopfzeile „Generated by codegen/generate.py … Do not edit“) werden nie von Hand geändert,
sondern über den Generator. Die CI prüft, dass der eingecheckte Stand dem Generator entspricht.

## Die Spec und wie der Generator damit umgeht

- Quelle: `https://<instanz>/system/runtime/swagger/openapi.json`, öffentlich und ohne Login abrufbar. Die Spec hängt
  nur an der ChurchTools-Version; bei gleicher Version ist sie auf verschiedenen Instanzen byte-identisch.
- Die Spec setzt jedes Schema direkt ein, statt per `$ref` zu verweisen. Jede eingesetzte Kopie ist aber identisch mit
  einem Eintrag in `components.schemas`. Der Generator gleicht das kanonische JSON ab und findet so die Namen (`Event`,
  `Person`, ...). Schemas ohne Gegenstück bekommen einen Namen aus ihrer Position, z. B. `ImageImageOptionCrop`.
- Die echte API weicht an einigen Stellen von der Spec ab. Die Live-Tests gegen eine Demo-Instanz haben diese Stellen
  gefunden. Der Generator gleicht sie aus, Details stehen in [`testbericht.md`](testbericht.md):
  - allgemeine Regeln: `deprecated`-Felder sind nie Pflicht; Zahlen werden als String akzeptiert und umgekehrt;
    `[]` gilt als leeres Objekt (PHP); das PHP-Nulldatum `-0001-11-30…` wird zu `None`; Array-Parameter bekommen `[]`
    im Namen; eine leere 204-Antwort ergibt `None`
  - Einzelkorrekturen in `FIELD_FIXES` und `RESULT_FIXES` in `generate.py`, jeweils mit Beleg
- Zeitstempel schickt der Client immer als `2026-11-01T10:00:00Z`. Der Server lehnt `+00:00` und Sekundenbruchteile ab.
- Felder, die nicht in der Spec stehen, gehen nicht verloren: In Python landen sie in `model_extra`, in Rust in `extra`.

Für eine neue ChurchTools-Version lädt `python3 codegen/generate.py --refresh` die Spec neu; danach zeigen die
Tests, was sich geändert hat. Die Spec liegt komprimiert in `codegen/spec/openapi.json.xz`, Version und Build in
`codegen/spec/info.json`.

Ob es eine neue Version gibt, prüft `.github/workflows/upstream.yml` täglich mit `codegen/check_upstream.py`: Hat die
Demo-Instanz (`demo.church.tools`, ohne Anmeldung) eine andere Version oder einen anderen Build **und** unterscheidet
sich ihre Spec von der gespeicherten (als JSON verglichen), legt der Workflow ein Issue mit Label
`churchtools-version` an: neue, entfallene und geänderte Operationen, möglicherweise inkompatible Änderungen
(entfallene Operationen, neue Pflichtparameter und Pflichtfelder in Bodies) und eine Checkliste. Eine neue Version
mit gleicher Spec (wie 3.138.0 → 3.138.1) erzeugt kein Issue. Live-Tests laufen weiterhin von Hand gegen eine
Test-Instanz, weil die nur befristet existiert und Zugangsdaten braucht. GitHub pausiert geplante Workflows nach
60 Tagen ohne Aktivität im Repository; dann unter *Actions* wieder einschalten.

## Bauen und testen

```bash
python3 codegen/generate.py              # generiert Code, Doku und Tests aus codegen/spec/openapi.json.xz
python3 codegen/generate.py --refresh    # Spec der aktuellen ChurchTools-Version herunterladen und ersetzen
pytest codegen/tests                     # Unit-Tests des Generators

cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace                   # Unit-Tests, Replay, Doku-Beispiele (Doctests); ohne Netz
cd python
uv venv && uv pip install --group dev     # Entwicklungswerkzeuge aus [dependency-groups] in pyproject.toml
maturin develop                          # baut _core und installiert das Paket editierbar
pytest tests                             # ohne Netz: Fake-Server, Replay, alle Doku-Beispiele ausgeführt
mypy --strict churchtools_api tests       # inkl. aller Python-Beispiele der Doku
ruff check ..
```

Voraussetzungen: Rust ab 1.88 (`rust-version` in `Cargo.toml`), Python ab 3.10, ein C-Compiler (die
TLS-Bibliothek `ring` enthält C-Code; CMake oder NASM sind nicht nötig).

### TLS

`reqwest` läuft mit `rustls` und dem Crypto-Provider `ring` (Feature `rustls-no-provider` in `reqwest`, `ring` in
`rustls`). Der Standard-Provider `aws-lc-rs` würde einen deutlich größeren C-Build mit CMake und unter Windows NASM
brauchen. Zertifikate kommen über `rustls-platform-verifier` aus dem Trust-Store des Betriebssystems, damit auch
selbst gehostete Instanzen mit eigener CA funktionieren.

### Doku-Beispiele werden ausgeführt

Jedes Beispiel steht nur einmal im Generator (`codegen/examples.py`, `codegen/guide.py`). Daraus entstehen die
Doku-Seite und die Tests:

- **Rust:** Jede generierte Methode trägt ihr Beispiel als Doctest im `///`-Kommentar; die IDE zeigt es beim
  Überfahren an. `cargo test --doc` führt es gegen die aufgezeichnete Antwort aus (`replay`-Feature, nur für die
  eigenen Tests) oder kompiliert es nur (`no_run`), wenn es keine Aufzeichnung gibt.
- **Python:** Das Beispiel steht im Docstring. `tests/test_doc_examples.py` führt alle Beispiele gegen einen lokalen
  Replay-Server aus (`tests/replay.py`); `mypy --strict` prüft zusätzlich alle Beispiele statisch.
- Beispiele aus Einstieg, Grundlagen und Projekten laufen genauso, außer sie sprechen bewusst einen festen Server an.

### Benchmarks

[`benchmarks/`](../benchmarks/README.md) misst einige typische Aufrufe offline gegen einen lokalen Server, in Rust und
Python, und vergleicht das Python-Paket mit reinen Python-Clients (requests, httpx, urllib3).

Ergebnis in Kürze: Der Rust-Transport macht einzelne Anfragen aus Python 2–6× billiger; bei großen Listen bestimmt
Pydantic die Zeit, und Rust kann daran nichts ändern, solange Python Pydantic-Modelle bekommt, weil das Erzeugen der
Python-Objekte (nicht die Validierung) den größten Teil kostet. Die Alternative, Rust-Objekte statt Pydantic-Modelle zu
liefern, wurde geprüft und verworfen: etwa doppelt so schnelles Dekodieren, aber eine andere Python-API ohne die
Pydantic-Oberfläche. Was der Kern stattdessen beiträgt, ist das Vorausladen der nächsten Seite.

### Tests gegen eine echte Instanz

ChurchTools bietet eine kostenlose [Test-Instanz](https://church.tools/en/test-churchtools/) an, die nach drei Tagen
gelöscht wird. Wie man sie anfordert und damit testet, beschreibt die Doku im Kapitel „Testen“. Die Live-Tests legen
dort Daten an und löschen sie wieder; eine Produktivinstanz ist dafür nicht geeignet.

```bash
export CT_URL=https://xyz.church.tools CT_USER=... CT_PASSWORD=...
export CT_MIN_INTERVAL=0.25              # Abstand zwischen Anfragen (Standard 0,25 s = 4 pro Sekunde)
pytest tests/live                        # alle GET-Endpunkte + Schreib-Szenarien, ca. 4 Minuten
python tests/live/summary.py             # Übersicht als Markdown
cargo test -p churchtools-api --test live -- --ignored   # Login, Rate-Limit und Kalender aus Rust
```

- `tests/live/test_read.py` ruft jeden GET-Endpunkt einmal über die generierte API auf. Die IDs dafür sucht ein
  Resolver über die passende Listen-Route (`resolve.py`).
- `tests/live/test_write*.py` sind Szenarien wie „Person anlegen, ändern, archivieren, löschen“. Jedes räumt hinterher auf.
- Erfolgreiche Antworten landen in `fixtures/recorded/`, aus den Szenarien auch die der Schreib-Endpunkte. Daraus werden
  **Offline-Unit-Tests**: `tests/test_recorded.py` validiert sie mit Pydantic, `core/tests/recorded.rs` dekodiert sie
  in die Rust-Typen. Beide laufen ohne Netz.
- `tests/live/redact.py` entfernt beim Aufzeichnen Zugangsdaten, Token-artige Werte und den Namen der Testinstanz.
  Vor einem Commit neuer Fixtures lohnt ein Blick, ob nichts durchgerutscht ist.
- `tests/live/seed.py` legt vor dem Lesetest Daten an, die eine frische Demo nicht hat (Treffen, Tickets, Kontoauszug,
  Sync-Verbindung, …), und entfernt sie danach wieder.
- Die Doku markiert Endpunkte, die noch nicht oder nicht ausreichend getestet sind, mit einem roten Sternchen.
- `fixtures/live-results.json` hält das Ergebnis jedes Endpunkts fest; `tests/live/expectations.py` listet die
  erwarteten Fehler mit Begründung.

## Sync und Async

Eine Python-Methode ist entweder normal (`def`) oder eine Coroutine (`async def`). `client.events.list()` kann also nicht
beides sein. Man braucht zwei Klassen, etwa `Client` und `AsyncClient`. In Rust gilt dasselbe:
`reqwest::blocking` und das asynchrone `reqwest` sind zwei APIs. Der Mehraufwand ist hier trotzdem klein:

- Die Endpunkte sind generiert. Der Generator erzeugt dann jede Methode zweimal, einmal mit `async`/`await`.
- Modelle, Fehler und Query-Aufbau sind für beide Varianten gleich.
- Handgeschrieben wäre nur der Transport: in Rust ein async-Client, in Python die Brücke über `pyo3-async-runtimes`.

Ein späterer Async-Client lässt sich also ergänzen, ohne die synchrone API zu verändern.

**Threads.** `Client` ist `Send + Sync` und lässt sich klonen (die Verbindungen und das Rate-Limit werden geteilt).
Aus Python heraus gibt der Kern während jeder Anfrage den GIL frei, mehrere Python-Threads können also denselben
Client gleichzeitig benutzen. Der Kern selbst startet Threads nur beim Vorausladen von Seiten (`PageFetcher` in
`core/src/client.rs`): ab der zweiten Seite wird die jeweils nächste in einem kurzlebigen Thread angefordert, während
der Aufrufer die aktuelle verarbeitet; in Python überlappt so die Netzwerkzeit mit der Pydantic-Dekodierung.
Was das bringt und warum das Dekodieren trotzdem in Pydantic bleibt, steht in
[`benchmarks/README.md`](../benchmarks/README.md).

## Öffentliche API und Stabilität

- Die Abhängigkeiten des HTTP-Stacks (reqwest, rustls) sind nicht Teil der öffentlichen Rust-API: Anfragen nehmen
  `churchtools_api::Method`, Transportfehler sind in `TransportError` gekapselt. `chrono`, `serde` und `serde_json`
  sind bewusst öffentlich, weil die Modelle ihre Typen verwenden.
- Python- und Rust-API sollen gleich bleiben: gleiche Optionen am Client, gleiche Fehlerklassen, gleiche Namen der
  Endpunkte (siehe `codegen/OPERATIONS.md`).
- Jede Änderung an der öffentlichen API kommt in `CHANGELOG.md`.

## Veröffentlichen

Releases laufen über `.github/workflows/release.yml`. Ein Tag `v<version>` baut die Python-Wheels (Linux x86-64 und
ARM64 als manylinux und musllinux, macOS Intel und Apple Silicon, Windows x86-64; abi3, also ein Wheel je Plattform
für Python ab 3.10), das sdist und das Crate-Paket, veröffentlicht auf PyPI und crates.io und legt ein
GitHub-Release mit dem Changelog-Abschnitt an. Von Hand gestartet (*Run workflow*) baut und testet er nur und
veröffentlicht nichts; so lässt sich der Paketbau vorab prüfen. Die Doku-Seite geht über
`.github/workflows/pages.yml` bei jeder Änderung an `docs/site/` nach GitHub Pages.

Veröffentlicht wird über Trusted Publishing (OpenID Connect): Im Repository liegen keine API-Token.

### Einmalig einrichten

- **GitHub, Settings → Environments:** `pypi` und `crates-io` anlegen, je mit *Required reviewers* (man selbst) und
  *Deployment branches and tags* auf das Tag-Muster `v*` beschränkt. Damit veröffentlicht nichts ohne Bestätigung.
- **PyPI:** unter *Your account → Publishing* einen *Pending publisher* anlegen: Projekt `churchtools-api-rs`,
  Owner `churchtools-api`, Repository `churchtools-api`, Workflow `release.yml`, Environment `pypi`.
- **crates.io:** Trusted Publishing lässt sich erst für eine bestehende Crate einrichten. Die erste Version daher von
  Hand veröffentlichen (`cargo login`, dann `cargo publish -p churchtools-api`), danach in den Crate-Einstellungen
  *Trusted Publishing* mit Repository `churchtools-api/churchtools-api`, Workflow `release.yml` und Environment
  `crates-io` eintragen. Der Workflow überspringt eine Version, die schon auf crates.io ist.
- **Settings → Pages:** Source *GitHub Actions*.
- **Settings → Security:** *Private vulnerability reporting* (darauf verweist `SECURITY.md`), Dependabot alerts und
  security updates, Secret scanning mit Push protection, Code scanning (CodeQL, *Default setup*).

### Checkliste für ein Release

1. `version` in `Cargo.toml` (Workspace) erhöhen; `cargo check` aktualisiert `Cargo.lock`.
2. Im `CHANGELOG.md` den Abschnitt `## [<version>] – <Datum>` anlegen bzw. „unveröffentlicht“ durch das Datum
   ersetzen. Der Workflow bricht ab, wenn der Abschnitt fehlt.
3. Die vollständige Prüfung aus `AGENTS.md` (Regel 5) laufen lassen, committen, auf `main` pushen und die CI
   abwarten.
4. Optional: den Release-Workflow von Hand starten und die Wheels prüfen.
5. `git tag -a v<version> -m "churchtools-api <version>"` und `git push origin v<version>`.
6. Die Veröffentlichung in den Environments `pypi` und `crates-io` freigeben.
